指定されたGitHub PRをレビューしてください。

## 対象PR

$ARGUMENTS

## 手順

### 1. PR情報の取得

`gh` CLIを使って以下の情報を取得する:

- `gh pr view <PR> --json title,body,baseRefName,headRefName,commits,files,additions,deletions`
- `gh pr diff <PR>`
- `gh pr view <PR> --json comments,reviews`（既存レビューがあれば把握する）

### 2. 全体像の把握

- PRのタイトル・説明から**意図と目的**を理解する
- コミット履歴から**変更の流れ**を把握する
- 変更ファイル一覧から**影響範囲**を確認する

### 3. 差分の詳細レビュー

変更されたファイルを1つずつ読み、以下の観点でチェックする:

#### バグ・ロジックエラー
- off-by-oneエラー、nullチェック漏れ、境界値の考慮
- エラーハンドリングの不備
- 競合状態やデッドロックの可能性

#### 設計・保守性
- 単一責任原則の違反
- 不必要な複雑さや過剰な抽象化
- 命名の適切さ
- 既存コードとのスタイル一貫性

#### セキュリティ
- インジェクション（SQL, XSS, コマンド等）
- 認証・認可の不備
- 機密情報のハードコード
- 入力バリデーションの不足

#### パフォーマンス
- N+1クエリ、不要なループ
- メモリリークの可能性
- 不要な再計算や重複処理

#### テスト
- テストが追加・更新されているか
- エッジケースのカバレッジ
- テストの可読性と保守性

### 4. レビュー結果の報告

以下のフォーマットで報告する:

```
## PR レビュー: [PRタイトル]

### サマリー
[PRの変更内容を1〜3行で要約]

### 指摘事項

#### 🔴 Must Fix（修正必須）
- [ファイル名:行番号] 指摘内容と理由

#### 🟡 Should Fix（修正推奨）
- [ファイル名:行番号] 指摘内容と理由

#### 💭 Nit（些細な改善提案）
- [ファイル名:行番号] 指摘内容と理由

#### 👍 Good（良い点）
- 良かった点を挙げる

### 総合判定
[Approve / Request Changes / Comment のいずれか + 理由]
```

- 指摘がない場合は無理に作らない
- 良い点も積極的に挙げる

## 引数の例

- `123` → カレントリポジトリのPR #123をレビュー
- `https://github.com/owner/repo/pull/456` → 指定URLのPRをレビュー
- `owner/repo#789` → 指定リポジトリのPR #789をレビュー
