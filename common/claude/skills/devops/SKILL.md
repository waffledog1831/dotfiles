インフラ・CI/CD まわりを構築・改善してください。

## 対象

$ARGUMENTS

（未指定の場合は、リポジトリ構成や会話の文脈から対象を判断する）

## 原則

- **既存構成を壊さない。** 変更前に既存の CI/CD 設定・Dockerfile・スクリプトを Read で確認する。
- **秘密情報を安全に扱う。** 認証情報・トークン・環境変数はハードコードしない。シークレット管理（GitHub Secrets 等）を使う。セキュリティ判断が必要なら確認を挟む。
- **本番影響を慎重に。** 本番環境に影響する変更はロールバック手順を考慮し、破壊的操作は事前に承認を求める。
- **環境差異を閉じ込める。** 「自分の環境では動く」を避け、コンテナ・設定で再現性を担保する。

## 手順

### 1. 現状把握

- 既存の `.github/workflows/`・`Dockerfile`・`docker-compose.yml`・デプロイスクリプトを Read で確認する
- 使用言語・ビルドツール・テストコマンド・デプロイ先を把握する

### 2. 構築・改善

対象ごとの要点:

| 対象 | 要点 |
|------|------|
| CI パイプライン | lint → test → build の段階構成。キャッシュ活用。失敗時に原因が分かるログ |
| CD / デプロイ | ビルド成果物の生成 → デプロイ → ヘルスチェック。ロールバック手段を用意 |
| Dockerfile | マルチステージビルド・レイヤ最適化・不要ファイル除外・非rootユーザー |
| docker-compose | サービス依存の明示・ボリューム・ネットワーク・環境変数の外出し |
| 環境構築 | セットアップ手順のスクリプト化・冪等性の確保 |

### 3. 検証

- CI 設定はワークフロー構文が正しいか確認する（`act` やドライランが使えれば活用）
- Dockerfile はビルドが通るか、可能なら実際に `docker build` で確認する
- テストが CI 上で確実に走る構成になっているか確認する

### 4. 安全確認

- シークレットがコードやログに露出していないか確認する
- 本番影響のある変更は影響範囲とロールバック手順を明記する
