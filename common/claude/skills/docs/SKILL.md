ドキュメントを作成・更新してください。

## 対象

$ARGUMENTS

（未指定の場合は、直近の変更内容や会話の文脈から対象を判断する。カレントの `git diff` / `git log` も参考にする）

## 原則

- **推測で書かない。** 不明な仕様は必ずコードを Read で確認してから書く。確認できないものは書かず、確認が必要な旨を明記する。
- **読む人の立場で書く。** 対象読者（開発者 / 利用者 / 運用者）を意識し、技術レベルに合わせた表現を選ぶ。
- **コードと矛盾させない。** 実際のコード・エンドポイント定義・設定を確認し、事実に基づいて書く。
- **既存ドキュメントのスタイルに合わせる。** 見出しレベル・言語・トーン・整形を既存ファイルに揃える。

## 手順

### 1. 対象と読者の確定

- 何を書くか（README / API仕様書 / ガイド / CHANGELOG / コードコメント）を確定する
- 誰向けか（開発者・利用者・運用者）を決める
- 既存の同種ドキュメントがあれば Read して構成・トーンを踏襲する

### 2. 情報収集

- 対象の実装コード・設定ファイルを Read で確認する
- API仕様書の場合は実際のエンドポイント定義・リクエスト/レスポンス型を確認する
- CHANGELOG の場合は `git log` で対象範囲のコミットを確認する
- 不明点があれば、推測せず「要確認」として残す

### 3. 執筆

対象ごとの要点:

| 対象 | 要点 |
|------|------|
| README | 概要 → 前提 → インストール → 使い方 → 構成。読んだ人がすぐ動けること |
| API仕様書 | エンドポイント・メソッド・パラメータ・レスポンス・エラー・例。実装と一致させる |
| ユーザーガイド | ゴールから逆算した手順。つまずきポイントに補足を添える |
| CHANGELOG | Keep a Changelog 形式を基本に、Added/Changed/Fixed/Removed で分類 |
| コードコメント | JSDoc/TSDoc 等。「なぜ」を書く。自明な「何を」は書かない |

### 4. 整合性の確認

- 書いた内容がコードと矛盾していないか最終確認する
- リンク切れ・古い記述がないか確認する
- 既存の目次・索引があれば追記・更新する
