# シンプル化

- 指定された対象と差分、関連する実装・仕様・テストを確認する。
- ドキュメントの意味とコードの外部から見える振る舞いを保ち、依頼範囲内で変更する。

## ドキュメント

- 重複、回りくどい説明、不要な前置きを削り、要点から短く具体的に書く。
- 関連する内容をまとめ、見出しや箇条書きは理解に役立つ場合だけ使う。
- 必要な仕様・制約・手順・使用例は残す。リンクやコマンドの正しさを確認する。

## コード

- 素直な制御フローと責務、意図が伝わる命名を優先する。
- 不要な分岐・状態・間接参照・抽象化を減らす。将来の仮定だけを根拠に設計を増やさない。
- 共通化は理解を助ける場合に限る。行数を減らすために処理を詰め込まない。
- 未使用と確認できたコードを削除し、エラー処理や境界条件は保つ。
- 説明用のコメントは原則書かず、必要な場合だけ設計判断や制約の理由（Why）を短く記す。処理内容（What / How）は命名と構造で表す。
- ライセンス表記やツール制御用の記述は保持する。

## 検証

- 変更に合ったテスト・構文チェックを実行し、意味や振る舞いが変わっていないことを確認する。
- 変更点・検証結果・未確認事項を簡潔に報告する。
