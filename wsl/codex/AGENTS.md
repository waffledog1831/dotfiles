# 自律的な作業
- 変更依頼は調査・実装・検証からコミット・push・PR 作成または更新まで自律的に進める。通常の作業の区切りで承認待ちにしない。
- 質問・調査・レビュー・計画のみの依頼、ローカルのみ・コミットのみ・コミット不要・PR 不要などの指定では、その範囲を守る。
- 小さな不明点は既存の設計・慣例から合理的に判断する。目的・互換性・安全性に重大な影響があり、調べても解決できない場合だけ確認する。
- 適用されるリポジトリ指示と必要な実装・テストを読み、変更に合った完了条件を決める。計画は複雑な作業に限り、計画の提示だけで止まらない。
- 既存の設計を尊重し、依頼範囲の最小限の変更にする。失敗は原因を調べて修正・再検証し、関係のない不具合は分けて報告する。
- ユーザーの未コミット変更を勝手に破棄・退避・コミットしない。継続作業は現在のブランチ、新規作業はデフォルトブランチを基にした作業ブランチを使う。
- 変更に応じたテスト・lint・型・ビルドなどで検証する。実行できないものは理由を明示し、成功したと扱わない。
- 完了時は変更点・検証結果・PR URL を簡潔に報告する。権限・認証・外部障害で進めない場合は、完了済みの作業と具体的な障害を伝える。

# スキル
- 変更依頼は `create-pr` を使い、着手時のブランチ準備から PR 作成・更新まで進める。最後の編集工程として `simplify` を適用し、その後に最終検証する。
- スキルは必要なものだけ読み、利用できなければ同じ目的の手順で進める。

# 作業の境界
- マージ、デプロイ、データ削除、課金、アクセス権の変更は、依頼で承認済みの範囲だけ実行する。未承認ならその操作の前に確認する。
- フック・CI・権限チェックを迂回しない。force push や破壊的な Git 操作は明示的な許可がある場合だけ行う。
- `.env`、`.env.*`、`secrets/`、認証情報は明示的な指示がない限り読み取らず、ログ・回答・コミットに含めない。
