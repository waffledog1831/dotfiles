# PR 作成・更新

1. 依頼の範囲を確認する。変更依頼には通常のコミット・push・PR 作成または更新まで含め、各段階で確認待ちにしない。質問・調査・レビュー・計画のみ、ローカルのみ、コミットのみ・不要、PR 不要の指定ではその範囲を守る。
2. 着手時に status、未ステージ・ステージ済みの diff、最近のコミット、現在のブランチ、リモート、デフォルトブランチ、既存 PR を確認する。継続作業は既存ブランチを使う。新規作業は fetch したデフォルトブランチの先端から `<種別>/<内容>` のブランチを作る。指定名を優先し、未指定なら命名して進める。無関係な未コミット変更があれば別ワークツリーを使い、勝手に stash・reset しない。デフォルトブランチは推測せず、fetch できなければ最新性の制約を明示する。
3. 依頼の完了条件と差分全体を照合し、不具合・互換性・機密情報・検証不足を確認して必要な修正を行う。最後の編集工程として `../simplify/SKILL.md` を依頼対象の差分へ適用する。
4. 最終差分に合ったテスト・lint・型・ビルドなどと `git diff --check` を実行する。失敗は原因を直して再検証する。必須の検証が失敗・未実行なら理由を記録し、公開可能な範囲を draft PR にする。機密情報が残る場合は公開しない。
5. 最終差分を確認し、依頼対象だけをステージする。無関係なステージ済み変更を混ぜず、分離できなければ確認する。日本語の `<prefix>: <変更内容>` でコミットし、帰属表記は実行ツールの設定に従う。コミット後に status を確認し、通常の push で作業ブランチを公開する。デフォルトブランチへの直接コミット・push、フックの迂回、未承認の force push は行わない。変更も既存の差分もなければ PR を作らない。
6. 同じ head と base の既存 PR があれば更新し、重複作成しない。タイトルと本文は日本語とし、テンプレートに従って具体的な変更後の挙動、検証結果、未確認事項を書く。複数行の本文は `gh pr create --body-file <file>` または API の構造化引数で渡す。
7. CI があれば結果を確認し、今回の変更に起因する失敗は修正・再検証・push する。待機できない場合は進行中・未確認と明記し、成功扱いにしない。修正後も最後にシンプル化と必要な検証を行う。
8. PR URL、変更点、検証結果、残る障害を報告する。認証・権限・ネットワークで進めない場合は作業を保持し、具体的な障害を伝える。マージ・デプロイは別途承認された場合だけ行う。
